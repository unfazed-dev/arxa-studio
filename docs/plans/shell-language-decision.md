# ADR: Shell language & platform strategy (Flutter vs Tauri)

- **Status:** Accepted (user-approved 2026-08-29, grill session)
- **Context docs:** `docs/research/flutter-desktop-webview-2026.md`, `docs/research/flutter-desktop-auto-update-2026.md`, `docs/plans/arxa-studio-grill-decisions.md`, `docs/plans/mobile-grill-decisions.md`, `docs/plans/rust-port-feasibility.md`

## Decision

1. **Desktop shell stays Tauri v2.** The Flutter-desktop spike failed:
   - No production precedent for a Flutter desktop app with an embedded webview as primary surface.
   - Open upstream keyboard-focus bug (flutter/flutter #147844) sits on arxa studio's typing-heavy core surface.
   - Windows webview options stale/young; Linux requires shipping Chromium (`webview_cef`); no silent in-place updater story comparable to `tauri-plugin-updater`.
   - macOS alone is viable (`webview_flutter` 4.14.1 + Sparkle 2), but a macOS-only rewrite re-solves solved problems for one platform.
2. **Mobile remote app is built in Flutter** (replaces the Tauri v2 mobile direction — Tauri's weakest leg):
   - Webview + native mix is mature on iOS/Android: native pairing/QR, push, biometric approvals, share sheets around a webview session view.
   - Unifies mobile with the arxa Dart system (`arxa/kit`) where the win is real.
   - Screen-level split rule: whole screens are either native or web; no interleaving within a screen.
3. **Engine unchanged:** dsh + pi remain TS sidecars behind the sidecar boundary (depend-don't-fork holds; see `arxa-harness-and-distribution.md`). Rust promotion is dead (`rust-port-feasibility.md`).
4. **Phase 3 stays triggered, not scheduled:** a Dart agent runtime modeled on pi's minimal-core design may replace pi behind the same sidecar boundary — only on a named trigger below.

## Re-check triggers (reopen desktop-shell question when any fires)

- Flutter Windows/Linux platform views ship (umbrella flutter/flutter #188375 leaves design-doc stage and lands stable).
- Keyboard-focus bug flutter/flutter #147844 closed and verified in a webview package.
- A named production Flutter desktop app ships an embedded webview as primary surface.
- Upstream dsh/pi failure or seam-blocked capability → evaluate Dart pi-style runtime (Phase 3).

## Current platform coverage (verified 2026-08-29)

- Tauri supports macOS (WKWebView), Windows (WebView2), Linux (WebKitGTK) with the updater plugin on all three; the updater endpoint is already target/arch-templated (`arxa-releases/.../{{target}}/{{arch}}/latest.json`).
- **Actually built today: macOS ARM64 only** — `desktop-release.yml` runs on `[self-hosted, macOS, ARM64, arxa]` with the `aarch64-apple-darwin` sidecar. Windows/Linux are planned build-matrix lanes (target triple + runner + bundle paths + per-platform signing), noted in the workflow but not yet wired.

## Post-decision updates (2026-08-29, user-approved)

- **cairn consumed in v1** via `arxa_kit_cairn` 0.1.0 (no stubbing); app generated by the `arxa` CLI scaffolder (dogfood).
- **FCM accepted** for Android push registration (cairn `registerPushToken` contract); APNs on iOS.
- **Android signing:** release signingConfig reads gitignored `android/key.properties`; keystore generated by `scripts/gen-android-keystore.sh` into `~/.arxa/secrets/` (never in repo); debug signing fallback when absent.
- Carried over from Tauri app: bundle id `solutions.arxadigital.arxa.mobile`, iOS team `43GNRCGQXQ`, webview UA `Mozilla/5.0 (Mobile) ArxaShell/0.1`.
- Biometric approvals deferred (no contract); Tauri `arxa/mobile` retired only after parity.

## Consequences

- Two shell technologies (Tauri desktop, Flutter mobile) — accepted cost; each is used where it is strongest.
- Windows/Linux desktop availability requires CI lanes + signing certs (Windows code-signing cert; Linux AppImage/deb), plus sidecar compilation per target triple.
- Mobile work item: Flutter remote app scaffold consuming the existing pairing/push contract (ADR-0037) — client-side port, not a redesign.
